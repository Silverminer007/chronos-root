## Context

Ticket #136. The Rust backend (`rust-backend/`) must be a drop-in replacement for the Java backend (`backend/`, the reference). Per-endpoint tests in each ticket check single endpoints; nothing checks the whole surface against the reference, or notices an endpoint that Rust still lacks. The harness was started before all endpoint tickets were merged, so it must not depend on the state of the Rust code.

## Decision

- **Location and language**: `contract-tests/`, Python 3 with the standard library only (no dependencies, no build step, runs on every CI runner). It lives outside `backend/` and `rust-backend/src/` so it does not collide with endpoint tickets. Tests are `unittest`.
- **One command**: `python3 -m parity` from `contract-tests/` (see its README). It **targets** two running backends by URL (`--java-url`, `--rust-url`). Starting the backends and seeding their databases (Flyway for Java, `rust-backend/migrations` baseline for Rust) is left to the caller, locally with Docker or in the cluster (#137), because both need Keycloak and a database whose setup differs per environment. The harness itself creates every row it needs through the API, so no SQL seed is shared between the two databases. The only seed prerequisite is therefore a fresh database with the schema of each backend (Flyway migrations without the test fixtures for Java, `rust-backend/migrations` for Rust) and, in the shared Keycloak realm, the test user, a second user (`CONTRACT_OTHER_USER_ID`, token `CONTRACT_USER2_TOKEN`) and an admin with role `ADMIN_API`; neither backend has a users table, so no user or role rows are seeded in the databases. The friendship between the two users is not seeded either: the scenario creates it (see "Amendment 2026-10-20" and the README, "Seed prerequisites").
- **Same users on both sides**: one bearer token per role (user, second user, admin for `/api/v2/admin/*`) is sent to both backends. Both validate against the same Keycloak, so the same token is the same test user. Tokens come from `CONTRACT_USER_TOKEN`/`CONTRACT_USER2_TOKEN`/`CONTRACT_ADMIN_TOKEN` or are fetched with a password grant (`CONTRACT_TOKEN_URL`, ...). Without a second-user or admin token the role falls back to the first user (the friendship steps of user 2 then run as user 1 and the admin steps compare the 403). No credentials are stored in the repository.
- **Scenario, not a request list**: `parity/scenario.py` is an ordered list of steps. Steps capture ids (`group`, `appt`, ...) from responses **per backend**, because generated ids differ. A step whose capture failed continues with id `0`, so the missing resource appears as a status mismatch and not as a silent skip.
- **What is compared** (`parity/compare.py`): status code; media type; JSON shape. The shape is field names and types, with `null` as its own type so null vs. missing vs. wrong type are distinct. Arrays: equal length, and the union of the element shapes (so one element with `null` and another with a string is one shape). Field order, generated ids, timestamps and other success-body values are **not** compared. **Error bodies (status >= 400) are also compared by value**, except the values of volatile keys (`timestamp`, `traceId`, ...; their presence and type are still compared in every body), because error messages are part of the contract. Plain-text success bodies (public key, health) are compared by presence and media type only.
- **Missing routes are never hidden**: Rust answering 404/405 where Java does not is the kind `missing_route`, but only if the Rust body is empty or lacks the application's error fields (`errorCode`/`message`/`fieldErrors`). A 404 with the application error body (resource missing) is a `status_mismatch`. The allowlist refuses to match it, so a missing endpoint fails the run until its ticket is merged.
- **Allowlist** (`contract-tests/allowlist.json`): entries `{step, kind, path, reason}` with glob patterns for step and path; an entry without a non-empty reason, or with unknown keys, makes the run fail with exit code 2. So does a `--allowlist` path that does not exist: a typo must not silently drop all deliberate differences and `rust_only` entries. Entries that match nothing are printed as notes so stale ones are removed. A second section, `rust_only`, lists Rust routes without a Java counterpart (`GET /api/v2/me`, `GET /health`), also with reasons.
- **Coverage mode** (`--coverage`): the endpoint list is taken from the Java sources (JAX-RS `@Path` + verb annotations; Quarkus built-ins `/metrics` and `/q/health/{live,ready}` are added by hand) and from the Rust `.route(...)` calls. Path parameter names are normalised to `{}`. It fails when a Java endpoint has no step or a Rust route has no Java counterpart and no `rust_only` entry. This is the acceptance check for "covers every endpoint".
- **Fixed request constants** (`parity/cli.py`, `parity/scenario.py`): the placeholders `{provider}` = `google` (a provider both backends support), `{unknown_provider}` = `does-not-exist`, `{missing_user}` = `does-not-exist` and `{missing_id}` = `999999999` (`MISSING_ID`) are hard-wired so that "not found" steps hit the same missing resource on both sides. They are part of the scenario, not configuration. Only `{other}` (`--other-user`/`CONTRACT_OTHER_USER_ID`) and `{redirect}` (`--redirect-uri`/`CONTRACT_REDIRECT_URI`, default `https://chronos.example.org/`, the redirect URI sent to the link endpoint) can be set from outside.
- **Authentication per role**: steps with `role=ROLE_ANON` (health, metrics, the unauthenticated-request step) are sent **without** an `Authorization` header on purpose, so that the 401 and the public endpoints are compared as an anonymous client sees them; all other steps carry the user (or, for admin steps, the admin) bearer token.
- **Step names are API**: allowlist `step` patterns are `fnmatch` globs (case-sensitive) against the step names in `parity/scenario.py`, and `path` patterns against the diff path. Renaming a step therefore silently detaches its allowlist entries (the stale-entry note then appears); rename steps together with `allowlist.json`.
- **Exit codes**: 0 all equal, 1 mismatch (or coverage gap), 2 harness error (unreachable backend, invalid allowlist, no token).
- **CI**: `.github/workflows/contract-tests.yml` runs the unit tests and `--coverage` on changes to `contract-tests/`, `backend/**/presentation` and `rust-backend/src`. The live comparison needs both backends and Keycloak and is run locally or by #137, not on this pipeline.

## Consequences

- Both backends mutate their database during a run (the cleanup steps remove what the scenario creates, but e.g. settings and the admin befriend step persist). Run against fresh databases for reproducible results.
- The Java source parsing is regex-based. A resource that builds paths dynamically would be missed; `--coverage` would then report the count mismatch only if the endpoint is not found at all, so new resource styles need a look at `parity/endpoints.py`.
- Pairs of steps in the scenario run against shared users, so the scenario relies on a second seeded user (`CONTRACT_OTHER_USER_ID`, default `oidc-user-2`).

## Amendment 2026-10-20 (ticket #137, first run against the deployed backends)

The first live run showed that the harness as first designed could not reach most endpoints. The decisions below extend the ones above; the run itself is recorded in `ARCH-2026-10-20-001-rust-java-parity-run`.

- **Second user with a befriend prelude**: Java only lets friends be added to groups and appointments (404 "Ihr seid nicht befreundet"), so with one user every participant step cascaded into 404. The scenario has role `ROLE_USER2` (`CONTRACT_USER2_TOKEN`, optional `CONTRACT_USER2`/`CONTRACT_USER2_PASSWORD` for the password grant) and, before the group steps, the steps `befriend: send request`, `befriend: second user lists incoming` and `befriend: second user accepts`. The friendship section then ends the friendship (`end friendship`, `end friendship twice`) before it re-creates requests, so `list friends` is no longer empty. Seed prerequisite: a second Keycloak user **and** a token for it; the friendship itself needs no seed.
- **Java management URL**: Quarkus serves `/q/health*` and `/metrics` on the management port (`quarkus.management.enabled`), not on the API URL as stated above. `--java-management-url`/`CONTRACT_JAVA_MANAGEMENT_URL` routes these paths there (`HttpTarget(management_url=...)`); unset, everything goes to the API URL (as before, and as for Rust, which serves them on the API port).
- **Request path in error bodies**: the `path` value of an error body contains generated ids (`/admin/appointments/2/...` vs. `/51/...`). Digits in `path` values are replaced before the value comparison, so ids are ignored but a different route is still a `value_mismatch`.
- **Capturing the whole body** (`capture={"agroup": "$"}`): Java answers `POST /api/v2/admin/groups` with the bare id, not an object, so the admin group step captures the body itself (`$`) instead of a field.
- **Allowlist and `missing_route`**: `missing_route` (Rust 404/405 without the application error body) stays not allowlistable. Deliberate Java defects (#162: 500 for missing token, missing fields or unknown enum values) are allowlisted as `status_mismatch` with a reason starting with `java-defect`; the Java 404 on the participation routes is a Java routing defect that is worked around by a local Java patch (`deployment/parity/java-participation-routes.patch`) and not allowlisted.
