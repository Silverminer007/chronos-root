## Context

The Nuxt 3 frontend needed state management for:
- Appointment list, filters, pagination
- Current user profile, permissions
- Notification queue
- Modal/dialog state
- Caching (avoid redundant API calls)

Options evaluated:
1. **Pinia** — official Vue 3 state library, simple, TypeScript-first
2. **Zustand** — lightweight, minimal boilerplate
3. **Tanstack Query** — focused on async data, built-in caching
4. **Nuxt auto-imports** — no library, just modules

## Decision

Use **Pinia** for all application state. Each store is a TypeScript function with composition API, containing both state and actions. Store actions call `$fetch` to mutate backend, then update local state.

### Key Choices
- **Pinia**: Official Vue 3 library, part of Vue ecosystem
- **Composition API**: Each store is a function, not a class
- **Colocation**: State + actions in same store (not separate reducers/actions)
- **No mutations**: Only state references and actions (mutations are implicit)
- **Auto-imports**: Stores auto-imported by Nuxt (`useAppointmentStore()` without import)

## Consequences

### Positive
- ✅ **Simple API**: Define state as `ref`, actions as functions
- ✅ **TypeScript**: All properties are typed, no `as any` nonsense
- ✅ **Devtools**: Pinia plugin for Vue DevTools, inspect state changes
- ✅ **Hot reload**: Stores update without page reload in dev
- ✅ **Colocation**: State + logic together, easier to understand
- ✅ **Composition API**: Same syntax as components (consistency)
- ✅ **No ORM-like complexity**: Just plain TypeScript, no magic

### Negative
- ❌ **No built-in persistence**: Requires manual `localStorage` save/restore
- ❌ **No built-in caching strategy**: Need to implement cache invalidation manually
- ❌ **Smaller ecosystem**: Fewer third-party extensions than Redux
- ❌ **No devtools defaults**: Must opt-in to devtools plugin

### Trade-offs
- **Simplicity vs. features**: Pinia is simpler, Tanstack Query has better caching
- **Centralized vs. distributed**: Store in one place (centralized), but means all state lives in one tree
- **Async handling**: Pinia doesn't handle async specially; actions are just async functions

## Alternatives Considered

### Tanstack Query (React Query)
```
Pros: Built-in caching, stale-while-revalidate, automatic background refetch
Cons: Overkill for Chronos; Pinia + custom cache is sufficient
Decision: Rejected — Pinia's simplicity better for this project
```

### Zustand
```
Pros: Minimal, lightweight
Cons: Less structure, requires more boilerplate, smaller ecosystem
Decision: Rejected — Pinia is official Vue library with better integration
```

### Nuxt auto-imports
```
Pros: Zero dependencies
Cons: No structure, state scattered across files
Decision: Rejected — centralized stores are cleaner
```

## Implementation Pattern

### Store Structure
```typescript
// app/stores/appointments.ts
export const useAppointmentStore = defineStore('appointments', () => {
  // State
  const appointments = ref<Appointment[]>([])
  const selectedAppointmentId = ref<number | null>(null)
  const loading = ref(false)
  const error = ref<string | null>(null)

  // Getters (computed)
  const selectedAppointment = computed(() =>
    appointments.value.find(a => a.id === selectedAppointmentId.value)
  )

  // Actions
  const fetchAppointments = async () => {
    loading.value = true
    try {
      const { data } = await useFetch('/api/v2/appointments')
      appointments.value = data.value
    } catch (e) {
      error.value = (e as Error).message
    } finally {
      loading.value = false
    }
  }

  const createAppointment = async (dto: CreateAppointmentDto) => {
    const created = await $fetch('/api/v2/appointments', {
      method: 'POST',
      body: dto
    })
    appointments.value.push(created)
    return created
  }

  return { appointments, selectedAppointmentId, loading, error, selectedAppointment, fetchAppointments, createAppointment }
})
```

### Usage in Components
```typescript
export default defineComponent({
  setup() {
    const store = useAppointmentStore()

    onMounted(() => {
      store.fetchAppointments()
    })

    return {
      appointments: computed(() => store.appointments),
      loading: computed(() => store.loading),
      selectAppointment: (id: number) => {
        store.selectedAppointmentId = id
      }
    }
  }
})
```

## Rules

1. **All data fetching in stores**: Components never call `$fetch` directly
2. **Stores are the source of truth**: Components read from store, not local state
3. **Actions are imperative**: Call `$fetch`, update local state, done
4. **Computed for derived state**: Use computed, not functions, for derived values
5. **Error handling in actions**: Catch and store errors, let component display them
